## 2. 핵심 판단 — 무엇을 "본체"로 삼을 것인가

### 2.1 VS Code 확장은 본체가 될 수 없다

VS Code 확장을 검토했지만 **본체로는 부적합**합니다.

- 그래프 캔버스·자료 편집·미리보기는 결국 **웹뷰(HTML/JS)** 로 만들어야 합니다. 그렇다면 UI는 어차피 웹앱입니다.
- VS Code 확장이 주는 실질 이득은 "이미 열려 있는 편집기 + 파일 접근 + git 통합"뿐인데, 이는 **로컬 웹앱 + Node API 서버**로 동일하게 얻을 수 있습니다.
- 반대로 확장으로 만들면 배포(VSIX/마켓플레이스), 확장 호스트 API 제약, 웹뷰↔확장 메시지 브리지라는 **추가 복잡도만** 생깁니다.

> **결론: UI를 웹앱으로 만들고, 원한다면 VS Code 확장은 "포장"으로 감싼다.** 확장의 웹뷰가 같은 UI를 로드하고 파일 브리지만 제공하는 형태(중복 개발 0).

### 2.2 기존 자산이 이미 절반을 해결한다

| 이미 있는 것 | 스튜디오에서의 역할 |
|---|---|
| `src/content.config.ts` (Zod 스키마) | 저장 전 검증의 **단일 기준** |
| `scripts/validate-content.ts` (R2~R15) | 저장/커밋 게이트. **그대로 재사용** |
| `docs/authoring.md` | 편집 UI의 필드 정의·툴팁의 근거 |
| `materials` 배열 + `FigureRef` | 자료 편집 UI의 데이터 모델 |
| M4 그래프 파이프라인(예정) | 그래프 편집기와 **동일한 레이아웃 엔진·뷰어 공유** |
| 디자인 토큰 | 스튜디오 UI도 같은 토큰 사용 |

즉 스튜디오는 "새 앱"이 아니라 **같은 데이터 모델을 다른 표면(表面)에서 다루는 도구**로 만드는 것이 핵심입니다.

## 4. 권장 아키텍처 — UI 1개 + 스토리지 어댑터 2개

```
┌──────────────────────────────────────────────┐
│  Studio UI (웹앱, Vite + TS)                 │
│  ├ 글 편집     ├ 자료 편집    ├ 그래프 편집    │
│  ├ 트랙 관리   ├ 검증 패널    ├ 미리보기      │
└───────────────┬──────────────────────────────┘
                │  공용 데이터 계층
        ┌───────┴────────┐
        │  content-core  │  스키마(Zod) · 검증(R1~R15)
        │  (공유 모듈)    │  content-index 생성 · 슬러그/리다이렉트
        └───────┬────────┘
                │ 스토리지 어댑터 (인터페이스)
     ┌──────────┼───────────┬──────────────────┐
     │          │           │                  │
  LocalFS     Git        GitHubAPI      FileSystemAccess
  (Node)   (commit)   (Contents/Git)     (Chrome 전용)
```

### 4.1 어댑터 인터페이스 (핵심 설계)

```ts
interface StorageAdapter {
  listContent(): Promise<ContentIndex>;          // 읽기
  readPost(id: string): Promise<PostRecord>;     // 파일 1개
  writePost(id: string, post: PostRecord): Promise<void>;
  deletePost(id: string): Promise<void>;         // git 이력으로 복구 가능
  readTracks(): Promise<Track[]>;
  writeTracks(tracks: Track[]): Promise<void>;
  readGraphOverrides(): Promise<GraphOverrides>;
  writeGraphOverrides(o: GraphOverrides): Promise<void>;
  putAsset(path: string, bytes: Uint8Array): Promise<void>;   // 이미지 업로드
  status(): Promise<ChangeSet>;                  // 변경 요약 (검증·diff)
  publish(message: string): Promise<PublishResult>;           // 커밋/푸시
}
```

- **LocalFS**: 로컬 클론을 직접 읽고 씀. 미리보기는 `astro dev`를 iframe으로 띄워 **100% 동일**.
- **GitHubAPI**: 저장소를 직접 읽고 씀. 설치 없이 브라우저에서 동작(모바일 포함).
- 둘 다 같은 UI·같은 검증을 쓰므로 이후 확장이 쉽습니다.

## 5. 선행 리팩터 (필수) — 5가지

GUI가 코드(TS) 파일을 수정하면 위험합니다. 아래 5가지를 **데이터/모듈로 분리**해야 스튜디오가 안전하게 동작합니다. 그리고 이 작업은 **M4(목차 그래프)의 선행 작업과 정확히 겹칩니다.**

| # | 현재 | 변경 | 이유 |
|---|---|---|---|
| 1 | `src/data/tracks.ts` (코드) | `src/data/tracks.json` + 얇은 래퍼 | GUI가 트랙을 안전하게 CRUD |
| 2 | `src/data/graph.overrides.ts` (예정, 코드) | `src/data/graph.overrides.json` | 그래프 편집기가 좌표를 저장 |
| 3 | `scripts/validate-content.ts` | `src/lib/validate.ts` (라이브러리) + CLI 얇게 | CLI·스튜디오가 **같은 검증** 공유 |
| 4 | 스키마가 `content.config.ts` 안 | `src/lib/content-schema.ts`로 추출 | Astro와 스튜디오가 같은 Zod 스키마 |
| 5 | (없음) | `npm run content:index` → `src/generated/content-index.json` | 스튜디오의 읽기 모델 = **M4 그래프 1단계와 동일** |

> **이 리팩터를 M4 앞에 배치하면 중복 작업이 0입니다.** 스튜디오를 나중에 만들더라도 지금 하는 것이 이득입니다.

## 6. 그래프 편집기 설계 (S2)

사이트의 목차 그래프와 **같은 데이터·같은 레이아웃 엔진(elkjs)** 을 씁니다. "편집기에서 본 모양 = 배포본 모양"이 되도록.

| 기능 | 동작 |
|---|---|
| 노드 | 글 1개. 트랙별 색, `draft` 흐리게, 고아 노드 경고 뱃지 |
| 노드 드래그 | 위치 이동 → `graph.overrides.json`에 좌표 고정(pin) |
| 엣지 생성 | 노드의 포트에서 다른 노드로 드래그 → 종류 선택(`requires`/`applies`/`related`/`cites`) |
| 엣지 삭제·변경 | 엣지 클릭 → 종류 변경/삭제 |
| **순환 차단** | curriculum(`requires`/`applies`)은 순환 금지 → 생성 즉시 검증, 위반 시 빨간 표시 + 저장 차단 |
| 자동 레이아웃 | ELK layered 재계산 버튼 (수동 위치는 유지) |
| 저장 | 양쪽 글의 frontmatter `links`에 반영(`related`는 자동 미러) |
| 미리보기 | 사이트와 동일한 URL 파라미터(`?focus=&hops=&kinds=`)로 필터·포커스 재현 |

## 7. 인증·발행 설계 (S4)

| 방식 | 비밀키 필요 | 토큰 수명 | 난이도 | 비고 |
|---|---|---|---|---|
| **fine-grained PAT** (로컬 보관) | 아니오 | 장기(만료 설정 가능) | 쉬움 | **1단계 권장.** 우리가 이미 써 봤음 |
| **OAuth App + Device Flow** | **불필요**(client_id만) | 장기/만료 | 중간 | 정적 페이지에서도 가능. 프록시 서버 불필요 |
| GitHub App + Worker 프록시 | 필요 | 8시간 + refresh | 어려움 | 가장 안전. 서버 필요 |

- `api.github.com`은 **CORS를 허용**하므로, 브라우저만으로 저장소 읽기/쓰기가 가능합니다(프록시 불필요).
- 발행은 **Git Data API로 커밋 1개**를 만들어 여러 파일을 한 번에 반영하는 방식이 안전합니다.
- ⚠️ **`.github/workflows/**`는 절대 건드리지 않습니다.** 워크플로 파일을 수정하는 커밋은 `workflow` 스코프를 요구하고, 사고 위험이 큽니다. 스튜디오가 쓰는 경로는 `src/content/**`, `public/blog/**`, `src/data/*.json` 뿐입니다.
- 토큰은 브라우저에 저장하지 않고 **OS 키체인/로컬 설정 파일**에 두는 것을 1순위로 합니다(원격 모드에서만 localStorage 고려).

### 발행 안전장치

1. 쓰기 전: 워킹트리 clean 확인 + `git pull --rebase`
2. 커밋 전: **항상** validator 실행 → 오류가 있으면 커밋 차단
3. slug/트랙 id 변경 시: **리다이렉트 자동 생성** (URL 불변 원칙 보호)
4. 삭제: git 이력으로 복구 가능하지만 확인 대화상자 필수
5. 커밋 메시지 규칙 자동 생성 (`post(sample): 제목`)

## 10. 리스크와 대응

| 리스크 | 대응 |
|---|---|
| 두 번째 제품이 되어 본업(글쓰기)이 밀림 | A1에서 **중단 가능**하도록 단계를 끊음. A3·A5는 선택 |
| 데이터 모델 이중화(사이트 vs 스튜디오) | 공용 스키마·검증(A0-3,4)으로 단일화 |
| 수동 편집과 스튜디오 편집 충돌 | git 기반 충돌 감지 + 쓰기 전 pull, 미리보기에서 diff 표시 |
| 프로덕션 번들에 관리자 코드 포함 | 스튜디오는 **별도 폴더/별도 빌드**. Astro `src/pages`에 두지 않음 |
| 토큰 유출 | 로컬 전용으로 시작. 원격은 Device Flow(단기 토큰) 또는 GitHub App |
| 미리보기와 실제 배포본 불일치 | 로컬은 `astro dev` iframe(동일 렌더러), 원격은 "근사 미리보기"임을 UI에 명시 |
| 그래프 편집기와 배포 레이아웃 불일치 | elkjs 설정을 **공용 모듈**로 공유 |

### 하지 않을 것

- Electron/Tauri로 편집기·파일트리·diff를 처음부터 만들지 않는다.
- Astro 사이트 빌드에 관리자 코드를 넣지 않는다(프로덕션 번들 오염).
- 자체 계정/인증 시스템을 만들지 않는다(GitHub에 위임).
- `.github/workflows/**`를 건드리지 않는다.
