## 2. 배치 결정 — 별도 저장소

**별도 private 저장소에서 개발한다.**

| 항목 | 확정 값 |
|---|---|
| 저장소 | **`ppaong/ppaong.writer`** (private, 생성 완료) |
| 로컬 경로 | **`~/Documents/ppaong.writer`** (맥) |
| 인증 | fine-grained PAT — 해당 저장소가 토큰 범위에 추가됨, push 권한 확인 완료 |
| 착수 시점 | **블로그(ppaong.github.io) M3~M7 완료 후** |

- 블로그 저장소(`ppaong.github.io`)는 **공개 사이트**이고, 스튜디오는 개인 도구다. 관심사·배포 파이프라인·의존성이 완전히 다르다.
- 블로그의 배포(Actions → Pages)에 도구 코드가 섞이지 않는다.
- 현재 `ppaong.writer`에는 README와 `.gitignore`만 있는 **착수 대기 상태**다.

### 2.1 별도 저장소의 유일한 대가 — 데이터 모델 공유

스키마·검증을 어떻게 공유할 것인가가 유일한 문제다. **해결책: 코드를 공유하지 않고 "계약"으로 공유한다.**

```
[블로그 저장소]                                   [스튜디오 저장소]
 src/content.config.ts   (Zod 스키마)             UI · 편집기 · 프리뷰
 scripts/validate-content.ts ──▶ CLI 계약 ──▶     계약 호출로 검증
   npm run validate:json      (JSON, 버전 고정)
```

**왜 코드 공유(npm 패키지/서브모듈)를 하지 않는가**
- npm은 **git 저장소의 하위 폴더**를 의존성으로 받는 것을 지원하지 않는다(`path:` 문법은 pnpm 전용).
- 스튜디오는 어차피 **로컬 클론 위에서** 동작한다. 즉 블로그 저장소의 파일이 항상 디스크에 있다.
- 따라서 **그 클론의 검증기를 실행**하는 것이 가장 정확하다. "그 저장소의 규칙으로 검증한다"는 것은 내용 편집기로서 올바른 의미론이기도 하다.
- 스키마가 바뀌어도 스튜디오가 **자동으로 따라간다**(버전만 확인).

## 3. 코어 계약 (Core Contract) — 블로그 저장소가 제공하는 인터페이스

현재 구현됨: `npm run validate:json` (또는 `node scripts/validate-content.ts --json`)

```jsonc
{
  "contractVersion": 2,          // 계약이 바뀌면 증가. 스튜디오가 확인 후 경고
  "ok": true,                    // 오류 0 여부
  "summary": { "posts": 3, "tracks": 1, "errors": 0, "warnings": 0 },
  "issues": [
    { "level": "error", "rule": "R3", "file": "sample/x.mdx", "message": "links.requires 의 'y' 를 찾을 수 없습니다." }
  ],
  "posts": [
    {
      "id": "sample/what-is-a-set",
      "track": "sample",
      "slug": "what-is-a-set",
      "url": "/blog/sample/what-is-a-set/",
      "title": "집합이란 무엇인가",
      "order": 1,
      "status": "published",
      "difficulty": 1,
      "tags": ["집합", "기호", "기초"],
      "materialCount": 3,
      "sectionCount": 4,
      "sections": [
        { "index": 1, "materialId": "fig-venn" },
        { "index": 2, "materialId": "note-symbols" },
        { "index": 3, "materialId": null },          // 빈 섹션
        { "index": 4, "materialId": "ref-wikipedia" }
      ],
      "updated": "2026-09-23"
    }
  ],
  "tracks": [{ "id": "sample", "postCount": 3 }]
}
```

### 계약 규칙

| 규칙 | 내용 |
|---|---|
| 종료 코드 | 오류가 있으면 `1`, 없으면 `0` |
| `--json` | **표준출력에 JSON만** 출력한다(사람용 메시지 없음) |
| 필드 추가 | 가능(하위 호환). 스튜디오는 모르는 필드를 무시한다 |
| 필드 변경·삭제 | `contractVersion` 을 올린다 |
| 스튜디오의 의무 | 실행 전 `contractVersion` 확인 → 다르면 사용자에게 경고하고 진행 여부를 묻는다 |
| 경로 | 스튜디오 설정에 블로그 클론 경로(`BLOG_PATH`)를 둔다 |

### 스튜디오가 블로그 저장소에서 건드리는 경로

| 경로 | 용도 |
|---|---|
| `src/content/blog/**` | 글 본문 + 프론트매터 |
| `public/blog/**` | 보조자료 이미지 |
| `src/data/tracks.json` | 트랙 정의 **(A0-1에서 JSON으로 이동 예정)** |
| `src/data/graph.overrides.json` | 그래프 좌표 **(A0-2, M4에서 도입 예정)** |

> ⚠️ **`.github/workflows/**` 는 절대 수정하지 않는다.** 워크플로 파일을 포함한 커밋은 `workflow` 스코프를 요구하고 위험이 크다.

## 4. 기능 명세

### 4.1 글 편집

- 목록: 트랙별 트리 + 검색 + `status`/`고아 노드` 필터
- 편집: 제목·요약·`order`·난이도·태그·`status` + 본문(마크다운)
- 본문 에디터: 코드 하이라이트, 수식 미리보기, `##` 자동 목차
- 삽입 버튼: `<Callout>`, `<FigureRef id="…" n={…}>`, 표, 디스플레이 수식(`$$` 3줄 형식 자동 생성)
- 저장 시: 계약 호출로 검증 → 오류가 있으면 저장/커밋 차단

### 4.2 보조자료(materials) 편집

- 자료 카드 CRUD, 순서 드래그, 그룹 지정
- 타입별 필수 필드 강제(`authoring.md` 4.2 표와 동일)
- **이미지 드래그&드롭 업로드** → `public/blog/<track>/` 에 저장 + `src` 자동 입력 + `alt` 입력 요구
- `FigureRef` 번호 자동 계산(자료 순서 변경 시 본문 참조 번호 일괄 갱신)

### 4.3 트랙(챕터) CRUD

| 동작 | 규칙 |
|---|---|
| 생성 | `tracks.json` 추가 + 폴더 생성, 예약어 검증 |
| 수정 | 제목·요약·난이도·상태. `id` 변경 시 **리다이렉트 자동 생성**(URL 불변 원칙) |
| 순서 | 드래그 정렬(배열 순서 = 표시 순서) |
| 삭제 | 소속 글이 있으면 차단 → "이동" 또는 "함께 삭제" 선택 |

### 4.4 발행

1. 쓰기 전: 워킹트리 clean 확인 + `git pull --rebase`
2. 커밋 전: **계약(검증) 실행 → 오류 시 차단**
3. 커밋 메시지 자동 생성(`post(sample): 제목`)
4. `git push` → GitHub Actions가 배포
5. PAT는 **OS 키체인**(macOS) / 자격 증명 관리자(Windows)에 보관. 코드·설정 파일에 저장하지 않는다

### 4.5 미리보기 + 뷰포트 전환 (S7)

- 블로그의 `astro dev` 서버를 띄우고 **iframe으로 실제 글 페이지**를 띄운다 → **100% 동일한 미리보기**
- 뷰포트 전환 버튼: `전체` / `1024px`(태블릿 가로) / `768px`(태블릿) / `390px`(휴대폰)
  - iframe의 `width`만 바꾸는 **간단한 구현**. 기기 프레임 이미지는 넣지 않는다
- 미리보기는 저장 후 갱신(HMR), 변경 중에는 "저장되지 않음" 표시

> 스튜디오 자체 UI는 모바일을 고려하지 않는다(데스크톱 전용 레이아웃).

| **S-1** | 글 목록 + 메타 편집 + 본문 편집 + 검증 표시 + 발행 (MVP) | 2~3일 |

## 6. 블로그 저장소에서 지금 준비해 둘 것 (완료/예정)

| # | 항목 | 상태 |
|---|---|---|
| 1 | `npm run validate:json` — 기계가 읽는 계약 (contractVersion 1) | ✅ **완료** |
| 2 | `tracks.ts` → `tracks.json` (코드가 아닌 데이터로) | 예정 (M4 전) |
| 3 | `graph.overrides.ts` → `graph.overrides.json` | 예정 (M4) |
| 4 | 검증 로직을 `src/lib/`로 승격 (CLI와 계약이 같은 코드 사용) | 예정 (스튜디오 착수 시 불필요해질 수 있음 — 계약으로 충분하면 하지 않음) |
| 5 | `content-index` 생성 (그래프 파이프라인 1단계) | 예정 (M4) |

> 2·3·5는 **M4(목차 그래프)의 작업과 겹친다.** 스튜디오를 안 만들더라도 M4 때문에 필요하다.

### 앞으로의 작업 원칙 (스튜디오를 염두에 둔 규칙)

1. **데이터는 코드에 두지 않는다.** 트랙·좌표·설정은 JSON/데이터 파일로 두어 도구가 안전하게 편집할 수 있게 한다.
2. **검증은 하나의 경로로만 노출한다.** 새 규칙을 추가하면 `scripts/validate-content.ts` 에 넣고, 계약 JSON에 반영한다.
3. **계약 형식을 깨면 `contractVersion` 을 올린다.**
4. **파일 경로 규약을 유지한다.** `src/content/blog/<track>/<slug>.mdx`, `public/blog/<track>/`. 도구는 이 규약에 의존한다.
5. **`.github/workflows/**` 는 도구가 만질 수 없는 영역으로 남긴다.**
